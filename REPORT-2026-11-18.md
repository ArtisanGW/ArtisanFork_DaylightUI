## 1. Bag and controller after a merchant or a fight (PR #99)

**Symptom.** After the game auto-sold junk and you walked away from the
merchant, the chat showed "Interface action failed because of an AddOn". The
bag then still opened but ignored the D-pad and B.

**Cause.** The game closes the bags when the merchant window closes. Daylight
told the controller one frame later, when the bag was the last window on the
controller's list. Emptying that list from addon code is refused.

**Fix.** The bag tells the game it's closing while the game is still closing
its own bags. On a controller the bag closes as a fight starts, so the D-pad
goes to the fight. After the fight, a bag that's still open gets the focus back.

Files: `DaylightUI_Bags/OpenClose.lua`, `Pad.lua`, `Windows/Frame.lua`.

## 2. Quest map in combat (PR #100)

- The quest journal's map ring and quest area were built the first time they
  were needed. Inside a window the controller manages, building them in combat
  is refused, so they now wait until the fight is over.
- The game's own windows, like the world map, kept the D-pad through a fight.
  They're now handed back with Daylight's windows and listed again after the
  fight.

Files: `DaylightUI_Quests/Journal.lua`, `Pad.lua`.

## 3. Quest tracker vanishing after a quest item (PR #101)

**Symptom.** Using the salve on the Barrens' sickly gazelles made the whole
tracker disappear until `/reload`.

**Cause.** The salve puts you in combat for about 30 s, and the tracker's fade
was set to "In combat", so the tracker faded out, item button included. Found
with `/dui questlog`.

**Fix.** When a quest item is used from the tracker, Daylight remembers the
target's name. The tracker stays shown while everything you're fighting has
that name. Anything else joining the fight fades it as usual. Checked in game.

Files: `DaylightUI_Quests/Items.lua`, `Tracker.lua`, `tests/test_quests.lua`.

## 4. World map hitch on a controller (PR #102, merged upstream)

With a controller, the map removes each quest pin one by one, and the game's
hidden quest list rebuilt itself after every removal: about 500 ms with 19
pins. While the Daylight journal covers that list, it no longer listens to the
map's quest pins. Measured with `/dui mappace deep`.

## 5. Quest-starting items

- Using a quest-starting item (Chen's Empty Keg) did nothing. The game puts such
  a quest on its pop-up list, which only the game's own tracker shows, and
  Daylight hides that tracker. Daylight's tracker now shows each offer with the
  "!" icon, and clicking it opens the quest.
- On a controller, X on a bag item now offers Use for an item that starts a
  quest, and the quest opens right away.

## 6. Closing the bag in a fight

**Symptom.** Opening the bag in a fight and closing it printed "Interface action
failed because of an AddOn", with no Lua error and nothing in BugSack.

**Cause.** The game hooks the `OnHide` of every window its controller navigation
has used, permanently. That hook calls a game function that refuses addon
callers in combat. So any close of the bag by Daylight's code in a fight was
refused. `/dui padtaint` caught the exact call stack:
`Motion.lua` `Hide` → game hook `HandlePanelClose` → `RemovePanelInfo`, refused.

**Fix.** In a fight, such a window isn't hidden. Its contents are hidden, it
goes transparent and ignores the mouse, and it counts as closed. It's hidden
for real once the fight is over. Opening it again in the fight brings it
straight back. This covers every Daylight window, not only the bag.

Files: `Pad.lua`, `Motion.lua`, `Windows/Feel.lua`, `tests/test_pad.lua`
(3 new tests).

## 7. Still open: closing the world map

At 14:37 the map's own close code (the close button, then `ClearBindings`, then
`SmartNavigation:SuspendCursor`) was already tainted when it ran. The
controller refused it, and from then on refused
`SetPreferredGamepadInteractTarget()`, blaming DaylightUI_Bags.

Findings so far:
- The addon the game blames isn't reliable. In other sessions it blamed
  Waylore, which has no controller code at all.
- Several addons add pins or panels to the world map: Waylore,
  Spoken_Places, AdventureGuideForever, DialogueUI, and Daylight's own Quests
  and Skins. The map's close code runs through all of them before it reaches
  the controller code. The latest snapshot shows Waylore's pin pool on the map.
- The game's `taint.log` can't help: it's rewritten on every reload, so the
  session with the error is always gone by the time it can be read.

Next step: play for a while with Waylore, Spoken_Places, AdventureGuideForever
and DialogueUI turned off. If the map close stops breaking the controller, the
cause is one of them, not Daylight.

## Debug tools (not for release)

| Command | What it records | Saved in |
|---|---|---|
| `/dui questlog` | Quest tracker shown/alpha/fade state, twice a second for a minute | `DaylightUIDB.questLog` |
| `/dui mappace [deep\|manual]` | Frame times while the world map opens and closes, per addon | `DaylightUIDB.mapPace` |
| `/dui padtaint [now\|clear]` | Controller state written by addons, every "Interface action failed" with its call stack, and world map fields addons wrote | `DaylightUIDB.padTaint` |
| `tools/game_reload.sh` | Reloads the running game after a new build is copied in (checked working) | |

`tools/game_reload.sh` installs a small local addon, `DaylightUI_DevReload`
(never shipped), and presses its key, Ctrl+Alt+Shift+F9, in the game. Fixed
today:
- It no longer depends on Daylight UI. The key clicks a secure button whose
  macro is `/reload`, so the game reloads at once, with no popup.
- The key moved from F12, which Steam takes for screenshots, to F9.
- The binding is now written `ALT-CTRL-SHIFT-F9`. The game only recognizes
  modifiers in that order, so the old binding never fired.
- When the script has just updated the addon, it asks for one `/reload` by hand
  instead of pressing a key the running game doesn't know yet.

Later in the day:
- It presses Escape before the key. A text box with the cursor (chat, the Send
  Mail fields) takes every key press, so the binding never fired from there.
- It checks that the game really reloaded. The game rewrites its saved
  variables on every reload, so the script waits up to 30 s for them to change.
  Exit 0 now means a reload was seen; the new exit 4 means it wasn't.
- On KDE Wayland it asks KWin to focus the game first (a small KWin script over
  D-Bus, through `qdbus-qt6`). KWin refuses `xdotool`'s activate while a
  terminal has focus, so the keys went nowhere. Checked from Konsole.
- In Claude Code, the reload now waits for a "🔄 RELOAD WOW NOW" choice in the
  chat. A local hook (`.claude/settings.local.json`, not in git) runs the script
  as soon as that's picked.

The saved logs are written to `WTF/.../SavedVariables/DaylightUI.lua` on `/reload`.
`/dui padtaint` stays on across reloads until it's turned off.

## Deliveries Forever (separate addon, not in this repo)

A new addon of its own, in `Addons/DeliveriesForever` next to this repo and in
the game's AddOns folder. It has no dependencies. With Daylight UI installed it
becomes a Daylight UI plugin, through `DaylightUI.API` only (`OptionalDeps`).
It started as "Reagent Post" and was renamed; its saved settings were carried
over to the new name.

When you're at the mailbox, it fills a mail for each kind of item and the alt
you picked for it, one batch after another. It never presses Send.

| Kind | Which items | Goes to |
|---|---|---|
| Reagents | Trade Goods, and anything the game marks as a crafting reagent | the alt picked in "Reagents to:" |
| Pelts | Trade Goods > Leather | "Pelts to:" |
| BoE | Bind on Equip items not bound yet | "BoE to:" |

- **Names.** On this server a character's name is "First Last", and that's what
  goes in To:. The addon learns each alt when you log into it.
- **Exclusions.** Alt-click an attached item to never send it, or exclude by a
  word in the name (`/dlv exclude camp`). The panel lists them.
- **Commands.** `/deliveries` or `/dlv`, and `/dui deliveries` with Daylight UI.
- **Controller fix.** Opening the Send Mail tab from addon code later made the
  game refuse `SetPreferredGamepadInteractTarget()` when the game menu closed,
  blaming the addon. The addon no longer opens tabs or shows the game's windows:
  you open Send Mail, and the mail fills as it shows.
- **With Daylight UI's mail window.** That window keeps the game's mailbox open
  out of sight. The addon checks whether the game's mailbox is on screen, so it
  needs nothing of Daylight UI's internals. When it isn't, the panel floats in
  Daylight UI's look (you can drag it), attaches the items at once, and shows
  the name to type in To:. The API has no way to fill Daylight UI's To: field. The
  panel closes when the mailbox does, and has its own X.

Checked by running the addon in plain Lua with stand-ins for the game, both on
its own and with a fake Daylight UI. In game, only the first version's fill was
confirmed; the full names, the BoE group, the controller fix and the plugin
haven't been checked in game yet.
